# Trellis: тестирование и план доработок

Как мы работаем: разработка идёт у владельца проекта, новые версии выкладываются в git. Тестировщик
забирает обновления из git, проверяет их на реальных данных (Azure DevOps и др.) и присылает обратную
связь, по ней мы дорабатываем и выкладываем следующую версию.

## Для тестировщика

**Первый запуск.** Нужны Node 22+, Python 3.13 и git.

```
git clone https://github.com/renf0x/trellis.git
cd trellis
curl -L -o arbor.py https://raw.githubusercontent.com/renf0x/context-arbor/main/arbor.py
npm install
npm run dev
```

`arbor.py` (память Context Arbor, нужна приложению для идей, знаний и истории) не хранится в этом
репозитории, его берут из [context-arbor](https://github.com/renf0x/context-arbor). Если в новой
версии сказано обновить Arbor, повторите команду `curl` выше.

Откройте http://127.0.0.1:5173. Папка `data/` не хранится в git: ключи, входы и настройки у каждого
свои. В «Настройках» введите свой ключ OpenRouter и/или войдите через свою подписку ChatGPT.

**Обновление до новой версии.**

```
git pull
npm install
```

Затем перезапустите `npm run dev`. Ваши настройки и данные в `data/` при обновлении сохраняются.

**Как сообщать о проблеме.** Одно сообщение на одну проблему:
- что делали (по шагам) и что ожидали;
- что получилось: точный текст ошибки или скриншот;
- версия: вывод `git log -1 --oneline`;
- для ошибок модели: провайдер и модель из подписи под сообщением в чате;
- ключи, токены и PAT в сообщения не вставлять.

**Что уже можно проверять.** Настройки моделей (OpenRouter, подписка ChatGPT), оба чата, статистика
токенов, идеи и задачи. Azure DevOps пока не подключён: это задача 6 ниже, о готовности сообщим.

## Для разработки

## Что это

Trellis — локальное QA-приложение. Оно тянет документацию и тест-кейсы (Azure DevOps API и локальные
Markdown/CSV), даёт ИИ-агенту сверять их, находить расхождения и предлагать правки, прогоняет сценарии
через Playwright и накапливает знания в памяти Arbor. Устроено как «лего»: неизменяемое ядро и
подключаемые модули.

## Запуск

Нужны Node 22+ и Python 3.13.

```
npm install
npm run dev          # сервер 127.0.0.1:4317 + веб 127.0.0.1:5173
npm test             # тесты всех пакетов (тесты arbor.py живут в context-arbor)
npm run typecheck
```

Откройте http://127.0.0.1:5173. Ключ OpenRouter вводится в «Настройках» (или переменной
`OPENROUTER_API_KEY`), подписка ChatGPT подключается кнопкой «Войти через ChatGPT».

## Структура

| Путь | Назначение |
|---|---|
| `packages/core` | Ядро: схема манифеста модуля, слоты UI, права, шина событий, контракт LLM-провайдера, типы учёта токенов. Менять только при крайней необходимости. |
| `packages/arbor-bridge` | Обёртка над `arbor.py memory … --json` (добавить/прочитать/обновить записи памяти). |
| `packages/llm` | Провайдеры: OpenRouter (любая модель по id, повторы при 429/5xx), подписка ChatGPT (OAuth как в Codex CLI/opencode, backend `chatgpt.com/backend-api/codex`), журнал токенов. |
| `packages/ui` | Общие React-компоненты для модулей: `ChatPanel`, клиент `/api/llm`. |
| `apps/server` | Fastify: реестр модулей, маршруты модулей `/api/m/<id>/…`, `/api/llm/*` (настройки, вход, чат NDJSON-стримом, статистика). |
| `apps/web` | Vite + React 19 + Tailwind 4; оболочка (сайдбар, центр, правая панель), модули грузятся лениво. |
| `modules/<id>` | Модули: `module.json` + необязательные `server/index.ts` (`register(ctx)`) и `ui/index.tsx`. Модуль без `ui` показывается заглушкой с номером этапа. |
| `data/` | Рантайм, не в git: `config/` (настройки), `secrets/` (ключи и OAuth-токены), `usage/ledger.jsonl` (токены), `vault/` (память Arbor приложения). |
| `memory/` | Память Arbor для разработки самого проекта; только у владельца, не в git. |

Готовые модули: `overview`, `ideas-tasks` (идеи в Arbor), `agent-chat` и `dev-chat` (рабочие чаты,
у каждого своя модель и своя корзина затрат), `settings` (подключения и модели), `token-stats`
(статистика: OpenRouter free, OpenRouter платные и подписка ChatGPT отдельно). Остальные — заглушки.

## Правила проекта

- Ядро (`packages/core`) не менять без необходимости; новое добавлять модулями.
- Секреты только в `data/secrets` или переменных окружения; в браузер не отдаются, в git не попадают.
- Любая запись во внешние системы (Azure, файлы) — только через предложение, подтверждённое человеком в UI;
  проверка на сервере, а не в промпте.
- Документы и кейсы для модели — недоверенные данные (prompt injection).
- `arbor.py` правится в репозитории `renf0x/context-arbor`, сюда он не коммитится.
- Версии в git выкладывает владелец; секреты и `data/` в git не попадают (`.gitignore`).

## План доработок

Делаем мы; порядок меняется по обратной связи тестировщика. Задачи 1–2 не зависят от Azure.

### 1. Проверить вход по подписке ChatGPT на живом аккаунте
Вход, список моделей и ответ модели уже проверены на живом аккаунте (Plus). Список запрашивается с
`client_version=1.0.0`: со старой версией backend скрывает новые модели. `gpt-6-astra` исключена по
просьбе владельца (слишком быстро тратит лимит), см. `EXCLUDED_CHATGPT_MODELS`. Осталось проверить обновление токена (через час после входа) и поведение при ошибках backend.
- Если `/codex/models` не отдаёт список, в UI будет запасной список (`FALLBACK_CHATGPT_MODELS` в
  `packages/llm/src/chatgpt.ts`): поправить разбор ответа.
- Если backend отвечает 400 про `instructions`, сделать запасной вариант: официальный промпт Codex в
  `instructions`, наш системный промпт отдельным сообщением `developer`.
- Готово, когда: ответ приходит, запрос виден в «Использовании токенов» как «ChatGPT · подписка»,
  через час работает обновление токена.

### 2. Сохранение истории чатов
Сейчас диалог живёт только во вкладке. Хранить диалоги (SQLite или JSONL в `data/`), список диалогов,
продолжение после перезагрузки. Готово, когда: после F5 диалог на месте, можно открыть прошлый.

### 3. Модель данных и хранилище
SQLite (`better-sqlite3`) в `data/`: нормализованные `Doc`, `TestCase`, `Link`, `Source`, версии/ревизии.
Готово, когда: есть миграции, репозиторий с тестами, данные переживают перезапуск.

### 4. Настраиваемые справочники
Статусы документов и кейсов, исходы прогонов, приоритеты, серьёзность находок, типы, теги. У значения:
ключ, название, цвет, порядок, флаги («закрывающий», «считать пройденным»), сопоставление со внешними
значениями каждого коннектора. Экран «Настройки → Справочники». Удаление используемого значения —
через выбор замены. Неизвестные внешние значения попадают в «несопоставленные».
Перевести `ideas-tasks` на справочник (сейчас статусы зашиты в `modules/ideas-tasks/server/index.ts`).
Готово, когда: переименование или удаление статуса мигрирует записи, всё пишется в историю.

### 5. Коннектор локальных файлов
Модуль `connector-local-files`: папка с Markdown (документы, дерево по папкам) и CSV (кейсы, маппинг
колонок настраивается). Ручная синхронизация и наблюдение за изменениями.
Готово, когда: документы и кейсы из папки видны в данных; изменение файла обновляет запись.

### 6. Коннектор Azure DevOps (чтение)
Модуль `connector-azure-devops`: организация, проект, PAT (в `data/secrets`); Wiki (страницы и дерево)
и Test Plans (планы, наборы, кейсы, шаги). Выяснить нужные права PAT и версии API, записать в
`memory/decisions.md`. Маппинг полей и work item types через справочники (задача 4).
Готово, когда: реальный проект синхронизируется, неизвестные статусы видны как «несопоставленные».

### 7. Экраны «Документация» и «Тест-кейсы»
Модули `docs-view` (дерево, рендер Markdown, статус/версия) и `testcases-view` (таблица, фильтры по
справочникам, шаги и ожидаемые результаты). Поиск в верхней строке.

### 8. Агент с инструментами
Цикл tool-calling в основном чате (контракт уже поддерживает `tools` и `tool-call` в обоих провайдерах).
Инструменты: `docs.*`, `cases.*`, `compare.*` (шаги кейса ↔ требования, находки с серьёзностью и
ссылками), `memory.*`. Передать модулям доступ к LLM через `ServerModuleContext` по правам
`llm:main`/`llm:dev`. Лента действий агента в чате. Находки с вердиктом «принять/отклонить».
Готово, когда: на заведомо расходящихся документе и кейсе агент находит расхождение.

### 9. Предложения правок и запись во внешние системы
Инструмент агента `propose_change` создаёт предложение (было/стало, обоснование). Статусы
`draft → pending → approved → applied | rejected | failed`; `applied` только по клику в UI (diff,
«Применить / Изменить / Отклонить»). Проверка ревизии Azure (`rev`) перед записью, снимок «до» для
отката, запись `CHG` в Arbor. Запись в коннекторе выключена по умолчанию.
Готово, когда: прямой вызов API в обход UI отклоняется сервером; откат работает.

### 10. Playwright-прогоны и отчёты
`@playwright/mcp` дочерним процессом через MCP-клиент; allowlist доменов в настройках; модуль
`runs-reports`: список прогонов, шаги, скриншоты, итог. Браузер: Chromium из Playwright (Edge на
машине владельца нет).

### 11. Знания агента («дообучение»)
Вердикты по находкам, глоссарий и подтверждённые правила сохраняются в Arbor как `KNW` и подмешиваются
в контекст агента (`arbor.py memory query`). Модуль `knowledge` для просмотра и правки.
Готово, когда: принятое решение учитывается в следующем ответе агента.

### 12. Dev-чат и задачи
Из dev-чата создавать `IDEA` в Arbor одной кнопкой / инструментом; «Обсудить задачу» в панели идей
открывает чат с её контекстом.

### 13. Аналитика
Токены: графики по дням, разрез по пользователю и задаче (free, платные и подписка по-прежнему раздельно).
Модуль `qa-analytics`: покрытие требований, доля расхождений, качество кейсов (дубли, без ожидаемого
результата, устаревшие), нестабильные прогоны, длительность.

### 14. История изменений и срок хранения
Снимки и диффы документов и кейсов, `CHG` в Arbor помесячно, настройка срока хранения в месяцах и
фоновая очистка. Модуль `history`.

### 15. Справка
Раздел «Справка»: идея продукта, инструкции. Делается последним.
