# Задача для Codex: проверить ошибку Jev 403 Cloudflare на машине тестировщика

## Контекст

Trellis — локальное приложение. Сервер работает на `http://127.0.0.1:4317`, интерфейс на `http://127.0.0.1:5173`.

Анализ «Сравнение и анализ» с движком Jev ходит в OpenRouter (`https://openrouter.ai/api/alpha/decisions`). На этой машине почти каждая проверка падает с ошибкой:

> Jev: 403, вместо ответа пришла страница Cloudflare («Attention Required! | Cloudflare»)

На машине разработчика тот же код и те же тексты проходят. Значит, причина, скорее всего, в окружении этой машины: сеть, прокси, VPN или блокировка клиента Node.

В обновлении есть две вещи:
- Новая логика Jev:
  - сначала повтор со смягчёнными символами;
  - затем пробный короткий запрос;
  - при блокировке всей сети анализ останавливается с понятной причиной и Ray ID.
- Скрипт диагностики `scripts/jev-check.mjs`.

**Твоя задача — только выяснить причину и прислать отчёт.** Код не меняй.

## Запрещено

- Выводить, логировать, копировать или пересказывать ключ OpenRouter. Не открывай и не печатай содержимое `data/secrets/*`: скрипт сам читает ключ и не показывает его.
- Коммитить, пушить, менять код, конфиги и настройки приложения.
- Записывать что-либо в Qase, Jira или Confluence. Не нажимай «Записать» и «Применить» в карточках правок и не вызывай `/apply`.
- Удалять или вручную править `data/` и `data-backups/`.
- Менять системные настройки, прокси, VPN или антивирус. Если для проверки нужна другая сеть, попроси тестировщика переключить её сам.

## Шаги

### 1. Версия

1. Обнови приложение обычным способом: запусти `update.cmd` в корне репозитория.
2. Убедись, что есть файл `scripts/jev-check.mjs` и в `docs/CHANGELOG.md` есть раздел «Jev и ошибка 403 Cloudflare». Если их нет, обновление ещё не опубликовано: остановись и сообщи об этом.
3. Запиши вывод `git log -1 --oneline` и `node -v`.

### 2. Окружение сети (без секретов)

1. Выполни `netsh winhttp show proxy`.
2. Выполни `ipconfig /all | findstr /i "adapter description"` и по описаниям адаптеров определи, есть ли VPN.
3. Выясни, заданы ли переменные `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS`. Достаточно имён, без значений. Скрипт из шага 3 тоже их покажет.
4. Выясни, есть ли корпоративная подмена сертификатов. Выполни:
   ```
   curl.exe -sv https://openrouter.ai/api/v1/models -o NUL
   ```
   и посмотри строку `issuer:`. Если издатель не публичный центр сертификации (не Google Trust Services, Let's Encrypt и т. п.), запиши его название.

### 3. Диагностика

1. В корне репозитория выполни:
   ```
   node scripts/jev-check.mjs > "%TEMP%\jev-check.txt" 2>&1
   ```
   Затем покажи содержимое файла. Скрипт шлёт около 20 коротких запросов к Jev; это доли цента.
2. Сверь результат с подсказкой в конце вывода:

   | Что видно | Причина |
   |---|---|
   | `tiny node` 403 HTML, а `tiny curl` 200 | Cloudflare режет клиента Node (TLS-отпечаток), а не сеть |
   | `tiny` 403 HTML и в node, и в curl | Заблокирован адрес сети (корпоративный прокси, VPN) |
   | `tiny` 200, а `url`, `json` или `header` 403 HTML | Фильтр по содержимому. Отдельно отметь, проходит ли `url_soft` |
   | 403 только в `burst` | Слишком много запросов сразу |
   | 401 или 402 | Ключ или баланс, не Cloudflare |

3. Если всё заблокировано, подожди 30 минут и запусти скрипт ещё раз, один раз. Запиши, изменилось ли что-то.

### 4. Проверка в приложении

1. Убедись, что приложение запущено: `start.cmd`, страница `http://127.0.0.1:5173` открывается.
2. Запусти небольшой анализ покрытия на Jev без модели чата. Это обычный запуск: прошлые результаты остаются в архиве запусков.
   ```
   curl.exe -s -X POST http://127.0.0.1:4317/api/m/compare/run -H "Content-Type: application/json" --data "{\"engine\":\"jev\",\"limit\":10,\"explain\":false,\"stages\":{\"quality\":false,\"coverage\":true,\"pairs\":false}}"
   ```
3. Каждые 10 секунд, но не дольше 10 минут, опрашивай `GET http://127.0.0.1:4317/api/m/compare/status`, пока `run.running` не станет `false`. Запиши `run.message`, `run.done` и `run.total`.
4. Выполни `GET http://127.0.0.1:4317/api/m/compare/coverage`. Посчитай `items` по `status` (`covered`, `partial`, `not_covered`, `unchecked`, `error`) и выпиши до трёх разных текстов `error`. Если ошибка длинная, достаточно первых 300 символов.
5. По тексту ошибки определи вариант:
   - «блокирует запросы с этого компьютера или сети… Анализ остановлен» — блок сети или клиента;
   - «не пропускает текст этой проверки» — фильтр по содержимому. Тогда запиши `id` требования и первые 200 символов его `text` (это текст документа, не секрет);
   - другое — приведи как есть.

## Отчёт

Пришли ответ в таком виде:

```
Версия: <git log -1 --oneline>, node <версия>
Прокси/VPN: <winhttp proxy; есть ли VPN-адаптер; имена proxy-переменных; издатель сертификата openrouter.ai>
jev-check: <полный вывод скрипта; Ray ID оставить>
Повтор через 30 минут: <если делался>
Анализ покрытия (limit 10): message=<...>, done/total=<...>, статусы: covered=.. partial=.. not_covered=.. unchecked=.. error=..
Ошибки: <до 3 текстов>
Вывод: <какой вариант из таблицы шага 3 и почему>
```
